# Tell me about a time requirements changed halfway through a project. How did you adapt?

**Definition:**  
The interviewer wants to know how you handle changing requirements without becoming frustrated or losing control of the project.

**Sample answer:**

> In one project, we were building a dashboard based on an initial set of requirements. Halfway through development, the Product Manager received new feedback from users and some of the requirements changed.
>
> Instead of immediately changing the existing implementation, I first clarified what had actually changed and which parts were still valid.
>
> I then identified the impact on the existing UI, API integration, and testing. We separated the changes into must-have requirements for the current release and improvements that could be handled later.
>
> I discussed the updated scope with the team and adjusted my implementation accordingly.
>
> Because we clarified the changes early and avoided rewriting unaffected parts of the feature, we were able to adapt without significantly disrupting the project.
>
> The experience taught me that when requirements change, the first step should be **understanding the change and its impact**, not immediately writing code.

**Good approach:**

> **Clarify → Assess impact → Re-prioritize → Communicate → Implement → Re-test**
